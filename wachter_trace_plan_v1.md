# План адаптации traceId в wachter (версия 1)

## Цель

Обеспечить продолжение внешней трассировки при проксировании HTTP-запросов через `wachter`, сохраняя корректный
`traceId` в downstream-сервисах и логах.

## Шаги

1. **Сбор входных заголовков**
    - Считать `traceparent`, `x-woody-trace-id`, `x-woody-span-id`, `x-woody-parent-id`, `x-woody-deadline`.
    - При наличии `traceparent` разобрать W3C-заголовок.
    - Если единственный идентификатор — `x-woody-trace-id`, использовать его как traceId; spanId/parentId сгенерировать
      при необходимости.

2. **Инициализация `TraceContext`**
    - Создать `TraceData` на основе входных значений:
        - Заполнить `serviceSpan` (traceId, spanId, parentId, deadline).
        - Если есть `traceparent`, проинициализировать OTEL span; иначе стартовать новый span, но с внешним traceId.
    - Установить `TraceContext.setCurrentTraceData(traceData)` до обработки запроса (без `createServiceFork`, либо
      использовать fork поверх подготовленного контекста).

3. **Логирование**
    - Убедиться, что `TraceContext` синхронизирован с MDC (`MDCUtils.putSpanData`) для попадания внешнего traceId в логи
      `wachter`.

4. **Проксирование**
    - Пересылать входные заголовки как есть, не переписывая traceId.
    - Если downstream ожидает дополнительные поля (`traceparent`, `x-woody-span-id`, `parent-id`), добавлять их на
      основе восстановленного контекста.

5. **Fallback**
    - При отсутствии trace-заголовков запускать новый `TraceContext` и логировать факт отсутствия внешнего traceId.

6. **Тестирование**
    - Юнит: кейсы с полным набором заголовков, только `x-woody-trace-id`, полное отсутствие заголовков.
    - Интеграция: проверить, что downstream сервис получает внешний traceId и логи содержат тот же идентификатор.

7. **Документация**
    - Обновить `wachter_trace_analysis.md` (и дополнительные материалы) с описанием новой логики и предположений по
      заголовкам.
